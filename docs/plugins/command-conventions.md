# Plugin Command Conventions

Two related conventions for any Threshold plugin with Android support, settled after
the July 2026 audit found drift on both ([#204](https://github.com/liminal-hq/threshold/issues/204)).

## COMMANDS is the webview-invokable surface only

A plugin's `build.rs` `COMMANDS` constant feeds `tauri_plugin::Builder::new(COMMANDS)`,
which generates the permission stub files under `permissions/autogenerated/commands/`.
That's its only job — it has no effect on which Kotlin `@Command` methods Rust can
reach via `run_mobile_plugin()`, since that's resolved by Kotlin reflection matching
the literal string at runtime, independent of this list.

**Rule:** only list commands that the webview actually calls via
`invoke('plugin:<name>|<command>')` — i.e. commands also passed to
`tauri::generate_handler![...]` in `lib.rs`. Commands reached exclusively via
`run_mobile_plugin` from Rust's own setup code (channel registration, the
pipeline-ready handshake) are Rust-internal and must not appear in `COMMANDS`. Listing
them there implies they need an ACL permission; they don't, and adding one only
papers over the fact that `run_mobile_plugin` bypasses the ACL entirely.

See `plugins/alarm-manager/build.rs` for a plugin with a real webview surface (five
commands) plus Rust-internal handshake commands kept out of the list, and
`plugins/alarm-manager/src/lib.rs`'s `acl_tests` module for an automated check that
every `COMMANDS` entry has a matching `allow-*` permission in `permissions/default.toml`.

## Kotlin `@Command` methods are camelCase

Kotlin's own coding convention is camelCase for functions, and every official Tauri
plugin (checked directly in `vendor/tauri-plugins-workspace`: clipboard-manager,
dialog, barcode-scanner, haptics, geolocation, biometric, fs, deep-link, opener,
shell, nfc, notification) follows it — Tauri has no competing convention of its own.

Rust command functions stay **snake_case** (idiomatic Rust); Kotlin `@Command`
methods are **camelCase** (idiomatic Kotlin). These don't need to match, because the
string passed to `run_mobile_plugin("...", ...)` is just a literal key that must equal
the Kotlin method name — it's independent of the enclosing Rust function's own name.
Upstream's `deep-link` plugin is the clearest example: `commands::get_current` (Rust,
snake_case) calls `run_mobile_plugin("getCurrent", ())` (bridge string, matching the
Kotlin method's camelCase name).

```rust
// Rust: snake_case function name, camelCase bridge string
pub fn stop_ringing(&self) -> crate::Result<()> {
    self.handle.run_mobile_plugin("stopRinging", ())...
}
```

```kotlin
// Kotlin: camelCase method name
@Command
fun stopRinging(invoke: Invoke) { ... }
```

This applies to every `@Command` method, whether or not it's webview-invokable —
Rust-internal handshake commands (`setAlarmEventHandler`, `markAlarmPipelineReady`,
`setWatchMessageHandler`, `markWatchPipelineReady`) follow the same camelCase rule as
commands the webview calls (`getLaunchArgs`, `stopRinging`).
